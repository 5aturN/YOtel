# Анализ безопасности кода ЯОтель

**Версия анализа:** прототип `v0.1.0`, состояние до работы №26. Проверены API-маршруты, схемы, ORM-запросы, конфигурация, локальные unit/API-тесты, Bandit и `pip-audit`. Результаты относятся к учебному прототипу и не являются сертификацией production-системы.

## Чек-лист

| Проверка | Результат |
|---|---|
| HTTPS/TLS | В FastAPI нет TLS-терминации; для production нужен HTTPS reverse proxy/managed ingress. Локальный HTTP допустим только для разработки. |
| Хранение паролей | На этой версии аккаунтов и паролей ещё нет; ввод пароля не реализован. Перед выпуском требуется регистрация с адаптивным хешированием, а не SHA-256 от пароля. |
| SQL injection | Запросы к базе построены через SQLAlchemy выражения и связанные параметры; динамической конкатенации SQL нет. |
| Проверка пользователя/владельца | Критический пробел: единый API key проверяет только интеграционный клиент, а не гостя; `guest_email` передаётся в теле запроса, бронирование не связано с аутентифицированным владельцем. |
| Валидация входа | Pydantic проверяет тип дат, число гостей и email; сервис повторно проверяет порядок дат, вместимость и занятость. |
| Секреты | API key читается из `YAOTEL_API_KEY`; значение по умолчанию отсутствует, `.env` исключён из Git. |
| Логи и персональные данные | В стандартном пути тело запроса не логируется; email хранится в записи бронирования и присутствует в ответе — требуется ограничить доступ и минимизировать выдачу. |
| Овербукинг | Репозиторий повторно проверяет пересечение и использует `SELECT FOR UPDATE` в PostgreSQL; конкурентный нагрузочный тест на настоящем PostgreSQL ещё не выполнялся. |

## Инструментальные проверки

- `bandit -r src/yaotel -ll`: **0 находок** уровней Medium/High. Bandit не обнаруживает проблему бизнес-авторизации V-01, поэтому ручной review обязателен.
- `pip-audit -r requirements-dev.txt`: **известных уязвимостей в проектных зависимостях не найдено** на дату проверки.
- Локальная тестовая среда первоначально содержала bootstrap `pip 25.0.1` с известными advisories; инструмент обновлён до 26.2.1 и повторная проверка только проектных зависимостей прошла без находок. Версия `pip` в пользовательском toolchain не включается в runtime-зависимости приложения.
- Ruff: `python -m ruff check src tests` — без замечаний.

## User stories и критерии приёмки безопасности

1. **Защита аккаунта:** пароль принимается только при соблюдении политики длины, хранится в PBKDF2-HMAC-SHA256 формате с индивидуальной случайной солью; исходный пароль и токен не попадают в логи или БД.
2. **Контроль доступа:** гость видит и изменяет только собственные бронирования; доступ к чужому ID получает 403; отрицательный сценарий покрыт API-тестом.
3. **Защита интеграции:** API key читается из среды и сравнивается constant-time; тесты проверяют отсутствие и неверное значение ключа.

В работе №26 будут реализованы V-01 и V-02, добавлены тесты пользователя/владельца и усилен вход. Остальные эксплуатационные меры остаются условием production-развёртывания.
