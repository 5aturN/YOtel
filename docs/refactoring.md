# Рефакторинг структуры API и бронирования

## Исходное состояние

На старте проекта в `src/yaotel/main.py` находились только создание FastAPI-приложения и `GET /health`. При добавлении предметной логики было бы неудобно держать маршруты, SQL-запросы, тарифы и правила пересечения дат в одном модуле.

## Структурное решение

| Модуль | Ответственность после рефакторинга |
|---|---|
| `main.py` | ASGI entry point; импортирует готовое приложение |
| `api.py` | HTTP-маршруты, API-key dependency, преобразование доменных ошибок в HTTP-коды |
| `services.py` | Проверка доступности, расчёт цены и создание бронирования |
| `repository.py` | SQL-запросы комнат и пересекающихся активных броней |
| `db.py` | Engine, сессии, схема и демонстрационный каталог |
| `models.py` | SQLAlchemy-модели комнаты и бронирования |
| `schemas.py` | Валидация входных данных и response-модели |
| `pricing.py` | Детерминированный расчёт суммы в копейках |

## Сохранение поведения и тесты

Health-check по-прежнему отвечает `200 {"status":"ok"}`. Новая логика доступности считает интервал полуоткрытым `[check_in, check_out)`, исключает неготовые комнаты и активные пересекающиеся брони. Создание выполняет повторную проверку непосредственно перед записью и использует `SELECT ... FOR UPDATE` на PostgreSQL для сериализации операций над одной комнатой.

Проверки: `python -m unittest discover -s tests -v` и `python -m pytest -q` — 10 тестов пройдены; Ruff и Bandit также проходят без замечаний. Тесты покрывают прежний health endpoint и новые сценарии API.

## Ограничение

SQLite используется для локальных тестов; конкурентное резервирование в production следует проверять на PostgreSQL. Электронная оплата и аутентификация гостя ещё не реализованы на этом шаге; общий API key — только межсервисный учебный gate и не должен считаться заменой пользовательской авторизации. Эти ограничения включены в последующие работы по безопасности и API.
