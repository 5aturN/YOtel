# Управление версиями и изменениями

## Ветвление

- `main` — проверенная стабильная линия; в неё попадают только подготовленные релизы.
- `develop` — интеграционная ветка следующего релиза.
- `feature/<короткое-имя>` — отдельное изменение; после тестов вливается в `develop` через `--no-ff`.
- `release/<semver>` — короткая ветка стабилизации, если потребуются только release-исправления.
- `hotfix/<описание>` — срочная правка production-версии с последующим переносом в `develop`.

Для каждого коммита используется осмысленное сообщение с номером практической работы и изменением, например `PR21: Refactor booking API into modular layers`. Автор Git-коммитов в учебном репозитории — `5aturN`; личные титульные сведения остаются в локальных Word-работах.

## Семантическое версионирование

Формат `MAJOR.MINOR.PATCH`: MAJOR меняет совместимость API, MINOR добавляет обратно совместимые функции, PATCH исправляет дефекты. Пока не завершены аутентификация, контроль доступа и интеграционные проверки, используется версия `0.1.0` — учебный прототип, не production-релиз. Целевой стабильный выпуск после завершения работ №15–30 — `1.0.0`.

## Выпуск и откат

Релиз проходит unit-тесты, Ruff, Bandit и сборку контейнера в GitHub Actions. После слияния проверенного `develop` в `main` создаётся аннотированный тег `vMAJOR.MINOR.PATCH`, а содержание фиксируется в `CHANGELOG.md`. Для проверки/отката доступна команда `git switch --detach v0.1.0`; после проверки возвращаются на нужную ветку. Версия `v0.1.0` помечает прототипный baseline.

Защита веток и обязательное одобрение Pull Request не менялись автоматически: для этого нужны отдельные правила владельца GitHub-репозитория.
