# Валидация требований системы «ЯОтель»

**Основание:** требования из практических заданий №1 и №4; изменение объёма из №6; проектные решения из №7–14. Проверка выполнена по полноте, однозначности, непротиворечивости и реализуемости.

## Результат проверки

Исходные требования описывали нужные функции, но часть формулировок нельзя было проверить: не были заданы граничные условия дат, правила блокировки номера, роли и права, источник статуса номера, измерительная нагрузка для времени поиска, срок хранения паспортных данных и поведение оплаты при сбое. Кроме того, статус «забронирован» смешивался со статусом физического номера, а оплата описывалась одновременно как обязательная и как необязательная. Ниже приведены согласованные формулировки для MVP.

## Уточнённые функциональные требования

| ID | Уточнённое требование и критерий приёмки | Статус/проверка |
|---|---|---|
| FR-01 | Гость задаёт даты заезда и выезда (ISO 8601, дата выезда исключается из интервала) и число гостей. API возвращает только чистые номера подходящей вместимости, свободные на весь интервал. При `check_out <= check_in` запрос отклоняется. | Расчёт даты/вместимости и поиск покрываются API-тестами; конфликт пересечения — 409. |
| FR-02 | До создания бронирования система показывает итоговую цену в RUB. В тарифе MVP пятничная и субботняя ночи умножаются на 1,15; остальные ночи — на базовый тариф. Сумма хранится и рассчитывается в копейках, округление — до целой копейки по правилу half-up. | Реализовано в `PriceCalculator`; unit-тесты проверяют будни, выходные, округление и границы. |
| FR-03 | При успешном бронировании система создаёт запись со статусом `pending`. Перед вставкой проверяется пересечение дат; активное бронирование той же комнаты на пересекающийся интервал не допускается. | Сервис бронирований; конфликт возвращает 409. |
| FR-04 | Гость может получить только свои бронирования и отменить собственное бронирование до заселения. Попытка прочитать или отменить чужую запись возвращает 403; отмена меняет статус, а не удаляет финансовую историю. | Будет проверено интеграционными тестами API. |
| FR-05 | Сотрудник рецепции может выполнить check-in только для подтверждённой брони и чистого номера; check-out переводит бронь в завершённое состояние. | Требование входит в целевую PMS, но не в текущий ранний API-прототип. |
| FR-06 | Горничная меняет статус номера только между `dirty`, `clean` и `inspected`; `out_of_service` устанавливает уполномоченный администратор. «Свободен» не является сохраняемым статусом — доступность вычисляется по интервалу и активным броням. | Состояния номера и права будут закреплены в модели и тестах. |
| FR-07 | После подтверждения бронирования гость получает email-ваучер. Если SMTP недоступен, бронь сохраняется, событие уведомления помечается ошибочным и журналируется без записи пароля/токена. Повторная обработка одного события не отправляет дубликат. | SMTP адаптер и идемпотентность проверяются с тестовым отправителем; живой SMTP требует конфигурации. |
| FR-08 | Управляющий получает отчёты по загрузке, ADR и RevPAR за выбранный период с указанием часового пояса и валюты. | Оставлено в целевом объёме; отчётный модуль не включён в учебный MVP. |

## Уточнённые нефункциональные требования

| ID | Уточнённое требование | Как проверять |
|---|---|---|
| NFR-01 Производительность | 95-й перцентиль ответа поиска — не более 2 секунд на эталонном стенде при 500 комнатах, 10 000 активных/исторических бронирований и 50 одновременных read-запросах. | Нагрузочный тест на staging; результат не заявляется до выполнения теста. |
| NFR-02 Доступность | Целевой месячный SLO — 99,9% для публичного API; planned maintenance исключается по согласованному календарю. | Мониторинг `/health`, журнал инцидентов и расчёт по месяцу; требуется развёрнутый staging/production. |
| NFR-03 Защита платежей | Приложение не хранит PAN/CVV. Карточные данные обрабатывает сертифицированный платёжный провайдер; приложение хранит только идентификатор и состояние транзакции. | Архитектурный review и тесты интеграционного контракта; подключение эквайринга вне текущего MVP. |
| NFR-04 Персональные данные | Для бронирования MVP хранит email и минимальные данные гостя; паспортные данные не принимаются и не сохраняются до определения правового основания, срока хранения и доступа. | Проверка схемы БД и OpenAPI; отдельный privacy review перед сбором документов. |
| NFR-05 Надёжность | Для production-базы должны выполняться ежедневные резервные копии; целевые RPO ≤24 ч и RTO ≤4 ч. | Восстановление тестовой копии и измерение времени восстановления до запуска production. |
| NFR-06 Локализация | Базовый интерфейс и сообщения об ошибках — на русском языке; даты API передаются в ISO 8601. | Проверка OpenAPI-примеров и пользовательского руководства. |

## Разрешение несогласованностей и границы MVP

1. **Статусы.** Состояние физического номера отделено от состояния брони. Для комнаты: `clean`, `dirty`, `inspected`, `out_of_service`. Для брони: `pending`, `confirmed`, `cancelled`, `checked_in`, `checked_out`. Значение «забронирован» получается из активной брони на дату, а не записывается в поле комнаты.
2. **Оплата.** Запрос бронирования создаёт `pending`; подтверждение зависит от результата провайдера оплаты или ручного действия сотрудника. Вариант «с предоплатой или без» задаётся тарифом, а не выбирается неоднозначно в одном запросе.
3. **Роли.** Канонические роли: `guest`, `receptionist`, `housekeeper`, `manager`, `administrator`. Назначение прав следует принципу наименьших привилегий; роли `admin` и `manager` в интерфейсе не считаются синонимами.
4. **Дополнительные услуги.** Бронирование конференц-зала и SPA принято как изменение объёма в работе №6, но отложено от MVP номеров: зал требует почасовых интервалов и собственной модели тарифа. Оно заносится в backlog следующего этапа, а не считается реализованным.
5. **Интеграции.** Электронные замки, channel manager, бухгалтерия и эквайринг не входят в первый учебный релиз. Для email предусмотрен адаптер SMTP; реальные параметры не хранятся в исходниках.

## Ключевые сценарии и трассируемость

| Сценарий | Условия/исключения | Проверка в проекте |
|---|---|---|
| Поиск номера | Даты корректны; число гостей не превышает вместимость; номер не выведен из эксплуатации; нет пересечения активной брони. | `PriceCalculator` unit-тесты; availability/API tests после реализации API. |
| Создание брони | Гость авторизован; номер доступен повторно проверяется в транзакции; цена фиксируется в копейках. | API integration test: успешное создание, неверный интервал, конфликт 409. |
| Отмена | Только владелец; `checked_in`/`checked_out` нельзя отменять; запись сохраняется. | API integration tests: владелец, чужой гость, недопустимый статус. |
| Email-подтверждение | Письмо отправляется после commit; ошибка SMTP не откатывает бронь; повторная обработка не дублирует письмо. | Тестовый sender и уникальный ключ события. |

## Итог

Критерии полноты, однозначности и согласованности зафиксированы в ID-формате; требования, которые нельзя подтвердить без стенда, платежного провайдера или SMTP-учётных данных, явно отмечены как непроверенные/отложенные, а не представлены как выполненные.
